# Contracts

This feature introduces no new or changed HTTP API or event schema of its own — it adds
*verification* of contracts that already exist elsewhere:

- **HTTP boundaries** (BFF↔products, BFF↔baskets, BFF↔orders): the authoritative contract is the
  BFF's own OpenAPI document, delivered by `007-bff-openapi-contracts`
  (`services/bff/src/Bff.Api/Features/{Products,Baskets,Orders}/*Endpoints.cs`,
  `GET /openapi/v1.json`). This feature does not redefine those shapes; the consumer-side pact tests
  in `Bff.Api.ContractTests` encode the subset of that documented shape the BFF's downstream clients
  actually depend on.
- **Event boundary** (`BasketCheckedOut`): the authoritative schema is
  `shared/EventContracts/schemas/BasketCheckedOut.v1.schema.json` and the matching
  `BasketCheckedOutV1` record, delivered by `008-versioned-event-schemas`. This feature does not
  add a new version or change the schema; the event pilot's consumer-side pact
  (`BasketCheckedOutConsumerPactTests` in `Orders.Api.ContractTests`) encodes the subset of that
  schema `orders` actually depends on.

What this feature *does* produce are the Pact documents themselves — the machine-readable record of
each consumer's expectations, generated by the consumer-side tests and verified by the provider-side
tests:

| Boundary | Pact file |
|---|---|
| BFF↔products | `pacts/bff-products.json` |
| BFF↔baskets | `pacts/bff-baskets.json` |
| BFF↔orders | `pacts/bff-orders.json` |
| BasketCheckedOut (orders↔baskets) | `pacts/orders-basketcheckedout.json` |

These files do not exist until the consumer-side tests run for the first time (Phase 2
implementation); this directory documents the boundary-to-file mapping decided in
[data-model.md](../data-model.md), not committed contract content.

See [research.md](../research.md) Decisions 1–4 for why Pact, why file-based exchange, and why the
event pilot targets `BasketCheckedOut` between `baskets` and `orders`.
