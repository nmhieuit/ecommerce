# Data Model: Consumer-Driven Contract Tests Across BFF/Service Boundaries

This feature has no domain/business data model — it adds test infrastructure. The "entities" below
are the test-artifact concepts named in spec.md's Key Entities section, described for implementers.

## Boundary

**Represents**: A named pairing of one consumer and one producer for a single interaction — either
an HTTP request/response or a published/consumed integration event. This is what User Story 3's
coverage audit enumerates (spec.md FR-008).

**Instances in this feature's scope** (fixed set of four; not an extensible runtime concept):

| Boundary | Consumer | Producer | Kind | Pact file |
|---|---|---|---|---|
| BFF↔products | `bff` | `products` | HTTP | `pacts/bff-products.json` |
| BFF↔baskets | `bff` | `baskets` | HTTP | `pacts/bff-baskets.json` |
| BFF↔orders | `bff` | `orders` | HTTP | `pacts/bff-orders.json` |
| BasketCheckedOut | `orders` | `baskets` | Event (message) | `pacts/orders-basketcheckedout.json` |

**Fields**: `Consumer` (service name), `Producer` (service name), `Kind` (`Http` \| `Event`),
`PactFilePath` (path under `pacts/`).

**Relationships**: Each `Boundary` has exactly one `Consumer Expectation` (the pact file's content)
and, once a build has run, zero or more `Verification Result`s (one per provider build run).

## Consumer Expectation (Pact)

**Represents**: The documented shape a consumer relies on from a specific producer interaction — a
Pact document (JSON) generated by the consumer-side test and read by the provider-side verification
test. For an HTTP boundary this is a set of request/response interactions (method, path, expected
response shape/status); for the event boundary it is an expected message body shape.

**Fields**:

- `Consumer` / `Provider` (service names, embedded in the Pact document per the Pact specification).
- `Interactions` (HTTP boundaries): one entry per BFF route exercised against that producer, each
  with a request description and the expected response shape/status the BFF's downstream client
  actually relies on (not every field the producer happens to return).
- `Messages` (event boundary only): one entry describing the expected `BasketCheckedOutV1` shape
  `orders` relies on.

**Lifecycle**:

1. The consumer-side test (`Bff.Api.ContractTests` for HTTP; `BasketCheckedOutConsumerPactTests` in
   `Orders.Api.ContractTests` for the event) runs, exercises a fake/mock producer configured with the
   consumer's expectations, and on success writes the Pact document to `pacts/`.
2. The Pact document is committed to the repository — it is the artifact User Story 3 audits, and
   the input the provider-side test reads.
3. A provider-side change to what a route returns (or what a checkout would construct) does not
   change this file; only a deliberate change to the consumer's own expectations does.

**Relationships**: Belongs to exactly one `Boundary`. Read by that boundary's `Verification Result`.

## Verification Result

**Represents**: The pass/fail outcome of a provider-side test running the producer's real behavior
(a real HTTP response from an in-process host, or a real constructed event payload) against its
`Consumer Expectation`, as part of that producer's own build (spec.md FR-001–FR-006).

**Fields**: `Boundary` (which pairing), `Passed` (bool), `FailureDetail` (populated only when
`Passed` is `false` — the specific interaction/field mismatch `PactVerifier` reports).

**Lifecycle**: Produced fresh on every run of the owning producer's `*.Api.ContractTests` project;
not persisted beyond the test run's own output (xUnit test result / CI log). A failing result fails
the producer's build, satisfying FR-005 and SC-002.

**Relationships**: Produced by exactly one `Boundary`'s provider-side test, reading that boundary's
`Consumer Expectation`.

## No changes to existing entities

`BasketCheckedOutV1` and `OrderPlacedV1` (`shared/EventContracts`) are read by the event pilot's
tests but not modified — no fields, versioning, or schema changes. The BFF's existing downstream
clients (`ProductsApiClient`, `BasketsApiClient`, `OrdersApiClient`) and each service's existing
route/handler code are exercised by the new contract tests but not changed by this feature.
