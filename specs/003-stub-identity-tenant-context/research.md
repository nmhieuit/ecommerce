# Phase 0 Research: Stub Identity with Resolved Tenant Context

All Technical Context fields were resolvable from the constitution, ADR-0001, the existing gateway/BFF/domain-service code from [002-gateway-bff-routing](../002-gateway-bff-routing/), and the roadmap's Phase 1 framing — no `NEEDS CLARIFICATION` markers remain. This document records the concrete decisions made on top of those already-settled choices, and the two gaps discovered by reading the current implementation rather than assuming it.

## Decision 1: The stub identity is a real (fake) `AuthenticationHandler`, not a hand-rolled header-stamping shortcut

**Decision**: Register a custom `AuthenticationHandler<StubIdentityAuthenticationSchemeOptions>` at the gateway via `AddAuthentication().AddScheme<...>(...)`. It always succeeds, producing a `ClaimsPrincipal` that carries a fixed tenant claim (and a fixed subject/user-id claim).

**Rationale**: Spec FR-007 requires that Phase 3's swap to a real identity server changes only the *resolution source*, not the propagation mechanism. Using the standard ASP.NET Core authentication extension point means that swap is registering `AddJwtBearer(...)` (validating tokens from the ADR-0001 identity server) in place of this scheme — the same claim, the same downstream code. A hand-rolled middleware that skips the authentication pipeline entirely would need a structural rewrite at that point, not a swap.

**Alternatives considered**: A plain middleware that stamps a hardcoded `X-Tenant-Id` header with no `ClaimsPrincipal` involved. Rejected — it satisfies today's tests but fails FR-007's actual intent, since Phase 3 would then be introducing the authentication pipeline for the first time rather than replacing one scheme with another.

## Decision 2: The gateway stamps `X-Tenant-Id` onto the *request*, exactly like `CorrelationIdMiddleware` already does

**Decision**: A `TenantHeaderPropagationMiddleware`, registered after authentication, reads the resolved principal's tenant claim and writes it to `context.Request.Headers["X-Tenant-Id"]` — never trusting or merging an inbound value, since Principle V requires the gateway to be the sole resolution point.

**Rationale**: `shared/ServiceDefaults/CorrelationIdMiddleware.cs` already established this exact pattern for the correlation ID, with the comment explaining why: "the gateway's reverse proxy copies inbound request headers... without this a generated ID would reach only this service's own response." The same mechanics apply identically to the tenant identifier — reusing a proven pattern rather than inventing a second one.

**Alternatives considered**: A YARP transform (`RequestHeaderFromClaim` via a custom `ITransformProvider`) configured declaratively instead of in code. Rejected for this feature — it would be the only YARP-config-driven behavior that depends on authentication state, breaking the otherwise clean split between "declarative static routing" (existing `ReverseProxy` config) and "code that reads request-specific identity." Revisit if the gateway grows more claims-to-header transforms later.

## Decision 3: A new shared `Tenancy` library, not four copies of the same middleware

**Decision**: Add `shared/Tenancy`, a class library sibling to `shared/ServiceDefaults`, providing `TenantContext` (a scoped holder with a `RequireTenantId()` guard that throws `MissingTenantContextException` when unresolved), `TenantContextMiddleware` (reads the inbound `X-Tenant-Id` header into it, and pushes the tenant id into the same kind of logging scope `CorrelationIdMiddleware` uses), and `TenancyExtensions` (`AddTenancy()` / `UseTenancy()`, mirroring `ServiceDefaults`' own `AddServiceDefaults()` / `UseServiceDefaults()` shape). Used identically by the BFF and all four domain services.

**Rationale**: Constitution Principle VII already established the precedent that a cross-cutting concern used identically everywhere is a shared component, not something "configured per service by hand" — the same reasoning applies to Principle V's tenant-resolution requirement. Four hand-rolled copies would let one service drift (forget the guard, log a different key name) in exactly the way a shared component prevents.

**Alternatives considered**: Putting `TenantContext` directly in `shared/ServiceDefaults`. Rejected — `ServiceDefaults`' own docstring scopes it to observability wiring specifically ("Shared cross-cutting wiring every service in the platform uses identically... observability MUST NOT be configured per service by hand"); tenancy is a distinct concern with its own lifecycle (request-scoped state, not just middleware), and the gateway needs `ServiceDefaults` without needing the *consumer* half of `Tenancy` (it only produces the header, via Decision 1/2, not consumes one via `TenantContextMiddleware`).

## Decision 4: A `DelegatingHandler` on the BFF's downstream clients closes a propagation gap that doesn't exist yet

**Decision**: Add `TenantPropagationHandler`, a `DelegatingHandler` attached to each of the BFF's four typed downstream `HttpClient`s (`services/bff/src/Bff.Api/DownstreamClients/`), that reads the current `TenantContext` and sets `X-Tenant-Id` on every outgoing request.

**Rationale**: Reading the current BFF implementation (`DownstreamClientRegistrationExtensions.cs`) confirms no such handler exists today — the BFF's typed clients only configure `BaseAddress` and a resilience pipeline. Typed `HttpClient`s do not automatically forward inbound request headers onto outbound calls; without this handler, spec FR-002 ("propagate... through gateway → BFF → services") would be false for the BFF → domain-service hop specifically, even though it holds for gateway → BFF (YARP forwards headers by default).

**Alternatives considered**: Also forwarding `X-Correlation-Id` through the same handler, since it has the identical gap (confirmed: nothing in the current BFF code forwards it downstream either, so today's downstream traces are not actually linked to the originating request past the BFF). Deliberately **not done here** — it's a real, already-mandated-by-Principle-VII gap, but it's outside this ticket's acceptance criteria and test scenarios, which are entirely about tenant context. Fixing it here would be scope creep dressed up as a two-line change. Flagged as a follow-up worth its own small ticket rather than folded silently into this one.

## Decision 5: Schema-per-tenant on the existing per-service database, not database-per-tenant

**Decision**: Each domain service's `DbContext` registration switches from `AddDbContext<T>(options => options.UseSqlServer(connectionString))` to the `(serviceProvider, options)` overload, which first resolves `ITenantContextAccessor.RequireTenantId()` (throwing if unresolved) and then configures the *same* per-service connection string already in `appsettings*.json`, with the `DbContext`'s `OnModelCreating` calling `modelBuilder.HasDefaultSchema(tenantId)` so the tenant's data lives in its own schema within that one database.

**Rationale**: Constitution Technology Constraints explicitly offers "database-per-service and schema-or-database-per-tenant" — schema-or-database, not database-only. Phase 1 has exactly one tenant (spec FR-008) and the existing `docker-compose.deps.yml` already provisions exactly one database per service. Schema-per-tenant satisfies Principle V's "connection resolved per request from the tenant context" (the resolved schema, not just a static connection string, now depends on the request's tenant) with zero new infrastructure — no new database, no new container, no docker-compose change — which matches a Phase 1 "walking skeleton" that the roadmap explicitly does not want hardened yet.

**AMENDED during implementation (Phase 4)**: the `HasDefaultSchema(tenantId)` half of this decision was **not implemented**; the `RequireTenantId()` gate was. The decision above did not account for migrations. The four services' existing migrations create their tables *unqualified* (`CreateTable(name: "Products")` with no schema), which SQL Server resolves to `dbo`, while a model carrying `HasDefaultSchema("contoso")` queries `[contoso].[Products]`. Verified empirically: `MigrateAsync` first refuses with `PendingModelChangesWarning`, and with that suppressed every query then fails with `Invalid object name 'contoso.Products'`. Making it work needs one of: migrations regenerated with the tenant schema baked in at design time (which pins them to a single tenant), or a custom `IMigrationsSqlGenerator` that qualifies null-schema operations with the model's default schema.

Neither was adopted for Phase 1. What US2 actually requires — "no persistence access without a resolved tenant" (spec FR-004/FR-005, Test Scenario 2, SC-003) — is delivered entirely by the gate at the single `AddDbContext` call site, which is what `TenantGatedConnectionScanner` and the four `TenantEnforcementTests` assert. Physical partitioning buys nothing while exactly one tenant is resolvable (spec FR-008) and is properly revisited alongside the database-per-tenant move this decision already earmarks for "once a second tenant actually exists". **A second tenant MUST NOT be introduced before that revisit**: today's services would serve both tenants from the same `dbo` tables, with only the gate — not the storage — keeping them apart.

**Alternatives considered**: A distinct database per tenant, with a tenant-keyed connection-string lookup (e.g., `ConnectionStrings:ProductsDb:{tenantId}`). Rejected for Phase 1 — it requires new per-tenant database provisioning in `docker-compose.deps.yml` for a single tenant that doesn't yet need it, and it would change the *shape* of `ConnectionStrings` configuration from a flat string to a nested per-tenant object, which the existing `ConnectionStringScanner` (`tests/CrossServiceIsolation.Tests`) does not read (see Decision 8). Database-per-tenant remains the right call once a second tenant actually exists; nothing in this design blocks migrating to it later, since the resolution is already behind `RequireTenantId()`.

## Decision 6: Persistence is tenant-gated at the single `AddDbContext` call site per service, not at every repository method

**Decision**: The ticket's Test Scenario 3 asks to "grep the codebase for any repository/DB call that does not require a tenant parameter" and expect zero results. This feature implements that guarantee structurally: each service has exactly one place a `DbContext`'s connection is ever constructed (its `AddDbContext<T>` registration in `Program.cs`), and that single call site is gated by `RequireTenantId()` (Decision 5). No individual query or repository method takes an explicit tenant parameter, because none can obtain a working `DbContext` instance without one already having been resolved. A new test, `tests/CrossServiceIsolation.Tests/TenantGatedConnectionScanner.cs`, extends the existing scanner convention to assert this call site exists, exactly once, per domain service.

**Rationale**: A structural guarantee at the one unavoidable choke point is stronger than a per-call-site convention (an explicit tenant parameter threaded through every repository method) — the latter compiles even when a developer passes the wrong or a placeholder tenant, where the former cannot be bypassed at all. This is a documented reinterpretation of the ticket's literal "parameter" wording, chosen because it more strongly satisfies the *intent* behind Test Scenario 3 (zero call sites can reach persistence without a resolved tenant) than the literal mechanism it describes.

**Alternatives considered**: Threading an explicit `tenantId` parameter through every repository/query method as it's written. Rejected as the primary mechanism — still adopted as a **secondary, defense-in-depth** documentation convention (methods that read `TenantContext` internally are still free to also accept a tenant parameter for clarity), but not relied upon for the actual guarantee, since there are no repository methods with real query logic yet (all four services are still scaffold-only per [001-scaffold-service-shells](../001-scaffold-service-shells/) and [002-gateway-bff-routing](../002-gateway-bff-routing/)) — nothing to grep for either way.

## Decision 7: Existing test-seeding helpers must set `TenantContext` directly, bypassing the middleware they don't run through

**Decision**: `TenantContext` is a plain scoped service with a settable `TenantId` (populated by `TenantContextMiddleware` during normal request handling), not something only reachable via the HTTP pipeline. Every existing seeding helper that resolves a domain service's `DbContext` directly from a manually created DI scope — confirmed present in `Products.Api.IntegrationTests/CatalogEndpointsTests.cs`, and identically in `Baskets`/`Orders`/`Parties.Api.IntegrationTests`' equivalent tests, plus `Bff.Api.IntegrationTests/BffTestHost.CreateDownstreamAsync` — must set `TenantContext.TenantId` on that same scope *before* resolving the `DbContext`, or the now-gated `AddDbContext` factory (Decision 5) throws `MissingTenantContextException` during test setup, not because of anything under test.

**Rationale**: This was found by reading the actual seeding code, not assumed. `CatalogEndpointsTests.CreateFactoryWithCatalogAsync` calls `factory.Services.CreateScope()` and resolves `ProductsDbContext` directly — no HTTP request, so no middleware, ever runs for that scope. Without this decision, Decision 5's enforcement would break all four services' existing integration-test seeding on day one of this feature, for a reason unrelated to what those tests actually verify.

**Alternatives considered**: Making `TenantContext` resolvable only through the middleware (e.g., an internal setter, or population that only a `HttpContext`-bound accessor can reach). Rejected — it would force every existing seeding helper to fabricate a fake HTTP request just to prime the DI scope, replacing a one-line fix (`scope.ServiceProvider.GetRequiredService<TenantContext>().TenantId = ...`) with a much larger one across four services for no additional safety; the guarantee this feature cares about (a *real request* cannot reach persistence unresolved) is unaffected either way, since test seeding is not a real request.

## Decision 8: No change to `ConnectionStringScanner`'s shape-reading

**Decision**: `tests/CrossServiceIsolation.Tests/ConnectionStringScanner.cs` continues reading flat string-valued `ConnectionStrings` entries unchanged.

**Rationale**: Decision 5 keeps each service's connection string exactly as it is today (one flat string per service); tenancy is expressed via `HasDefaultSchema`, not a nested per-tenant connection-string block. The existing isolation scan therefore stays meaningful with zero changes.

**Alternatives considered**: N/A — this decision exists to make explicit that Decision 5's rejection of database-per-tenant was made partly *because* of this scanner's current shape, so a future feature that does move to database-per-tenant knows it must revisit `ReadConnectionStrings` (which currently skips any property whose `ValueKind` isn't a plain string) at that time.
